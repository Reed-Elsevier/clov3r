# infra/ — AWS (Terraform)

**Stage 1 (current): shared dev database + Bedrock, no tools on laptops.**
Terraform runs in **AWS CloudShell** (a browser terminal inside the AWS
console). Laptops only need Node/npm (already used by the app) and temporary
credentials copied from the SSO portal. The Next.js app runs locally against
RDS and calls Bedrock directly.

```
AWS CloudShell (browser) ──terraform apply──► VPC + RDS Postgres 17 (ap-southeast-1)
                                                    ▲ 5432, TLS verified, allow-listed IPs only
laptop: npm run dev / db:migrate ───────────────────┘
laptop ──(temporary SSO credentials)──► Amazon Bedrock
```

| Path | What |
|---|---|
| `bootstrap/` | One-time S3 bucket for shared Terraform state (versioned, encrypted, TLS-only) |
| `main.tf`, `variables.tf`, `outputs.tf`, `versions.tf` | Root stack (region `ap-southeast-1`, S3 backend with native locking) |
| `modules/network` | VPC `10.40.0.0/16`, 2 public + 2 private subnets (private ones for ECS later), no NAT |
| `modules/rds` | Postgres 17 `db.t4g.micro`, encrypted, `rds.force_ssl=1`, reachable only from `db_allowed_cidrs` |
| `scripts/write-env.mjs` | Laptop helper: fills `DATABASE_URL` in `.env.local` from the RDS secret and tests the connection |
| `scripts/bedrock-smoke-messages.json` | Payload for a Bedrock smoke test in CloudShell |

**Security model:**
- The database is only reachable from the exact IPs listed in
  `db_allowed_cidrs`. `0.0.0.0/0` is rejected by validation.
- Every connection uses TLS, verified against Amazon's RDS CA
  (`sslmode=verify-full`).
- The master password is generated by RDS and stored in Secrets Manager. It is
  never in `.tf` files or Terraform state, and RDS rotates it every 7 days.
  If the app suddenly gets "password authentication failed", re-run
  `write-env.mjs`.

**Rough cost:** about US$30/month (≈ $1/day): RDS micro + 20 GB, one public
IPv4, one secret. Bedrock is pay-per-token on top. See [Teardown](#teardown).

## 1. Check guardrails (once, with your cloud platform team)

Company accounts often restrict things with SCPs or permission boundaries.
Ask before applying, or if anything fails with `AccessDenied` / `explicit deny`:

- Is a **publicly accessible RDS instance** (locked to specific IPs) allowed?
  Is creating a VPC and internet gateway allowed?
- Are **AWS CloudShell** and the SSO portal's **"Access keys"** (temporary
  credentials) enabled for your role?
- Are tags mandatory? Set them via `extra_tags` in `terraform.tfvars` (and the
  same `-var` for `bootstrap`).
- Bedrock / AWS Marketplace permissions (see step 5).

## 2. Create the infrastructure (ONE person, in AWS CloudShell)

Open the AWS console for the project account (via the SSO portal), switch to
**Asia Pacific (Singapore) ap-southeast-1**, and click the CloudShell icon.

**Get the code.** On GitHub, open branch `infra/aws-dev-backbone` →
**Code → Download ZIP**. In CloudShell: **Actions → Upload file**, then:

```bash
unzip -q clov3r-*.zip && mv clov3r-*/ clov3r && cd clov3r
```

(Or `git clone` with a GitHub personal access token.)

**Install Terraform in CloudShell** (persists in your CloudShell home folder,
nothing touches your laptop):

```bash
mkdir -p ~/bin && export PATH="$HOME/bin:$PATH"
ARCH=$(uname -m | sed 's/x86_64/amd64/;s/aarch64/arm64/')
curl -fsSL -o /tmp/tf.zip "https://releases.hashicorp.com/terraform/1.16.5/terraform_1.16.5_linux_${ARCH}.zip"
unzip -o -q /tmp/tf.zip -d ~/bin && terraform version
# CloudShell home is capped at 1 GB; keep provider binaries in /tmp
export TF_PLUGIN_CACHE_DIR=/tmp/tf-plugin-cache && mkdir -p "$TF_PLUGIN_CACHE_DIR"
```

**Create the state bucket** (once per account):

```bash
terraform -chdir=infra/bootstrap init
terraform -chdir=infra/bootstrap apply
terraform -chdir=infra/bootstrap output -raw backend_hcl > infra/backend.hcl
```

Keep `infra/bootstrap/terraform.tfstate` (it stays in your CloudShell home).

**Allow-list your team's IPs.** Each teammate opens
<https://checkip.amazonaws.com> on their laptop and sends you the IP.

```bash
cp infra/terraform.tfvars.example infra/terraform.tfvars
nano infra/terraform.tfvars        # db_allowed_cidrs = { name = "IP/32", ... }
```

**Apply** (RDS takes ~10–15 minutes):

```bash
terraform -chdir=infra init -backend-config=backend.hcl
terraform -chdir=infra plan -out tfplan
terraform -chdir=infra apply tfplan
```

CloudShell sessions time out when idle, and `/tmp` is wiped. In a new session,
re-run the two `export` lines above, then `terraform -chdir=infra init
-backend-config=backend.hcl` before `plan`/`apply`. State lives in S3, so
nothing is lost.

**Someone's IP changed / new teammate?** Edit `db_allowed_cidrs` in
`infra/terraform.tfvars` and re-run `plan` + `apply` (takes seconds).

## 3. Connect your laptop (everyone)

**Credentials.** In the SSO access portal, find the project account → role →
**Access keys**. Copy the three values into `.env.local` at the repo root
(create it from `.env.example` if missing):

```
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
AWS_SESSION_TOKEN=...
```

They expire after a few hours. Paste fresh ones when AWS calls fail.
`.env.local` is git-ignored; never commit credentials.

**Database URL + connection test:**

```powershell
npm install                           # once, after pulling this branch
node infra/scripts/write-env.mjs      # writes DATABASE_URL, downloads the RDS CA, tests the connection
npm run db:migrate                    # first time only (one person): creates the schema
```

If it can't connect, the script tells you why: usually your current public
IP isn't in `db_allowed_cidrs`, or your network blocks outbound port 5432.

## 4. Load the dataset

Once `feat/ingestion-api` lands, run its loader from your laptop. It uses
`DATABASE_URL` from `.env.local`. See `scripts/load-dataset/README.md`.

## 5. Bedrock (once per account, then everyone)

Most Bedrock models are enabled by default. Your SSO role needs
`bedrock:InvokeModel*` plus the `aws-marketplace:Subscribe`,
`aws-marketplace:Unsubscribe` and `aws-marketplace:ViewSubscriptions`
permissions (see the [model access docs](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)).

1. **Anthropic models:** one person opens the model in the Bedrock console
   **Model catalog** (ap-southeast-1) and submits the one-time *use case*
   form. It can stay "pending" for a while; AWS emails when done.
2. Pick a model. Newer models in Singapore are usually invoked through
   cross-region **inference profiles** (`apac.` / `global.` prefixes).
   List them in CloudShell:

   ```bash
   aws bedrock list-inference-profiles --query "inferenceProfileSummaries[].inferenceProfileId"
   aws bedrock list-foundation-models --by-provider anthropic --query "modelSummaries[].modelId"
   ```

   `apac.` profiles keep requests within Asia-Pacific regions. `global.` ones
   can route worldwide and may be denied by a company SCP.
3. Smoke test in CloudShell (or use the console **Playground**):

   ```bash
   aws bedrock-runtime converse --model-id <MODEL_OR_PROFILE_ID> --messages file://infra/scripts/bedrock-smoke-messages.json
   ```

4. Everyone sets `BEDROCK_MODEL_ID=<MODEL_OR_PROFILE_ID>` in `.env.local`.
   The app's AWS SDK picks up the credentials from step 3 automatically.

## Teardown

In CloudShell: `terraform -chdir=infra destroy`.

To pause costs without destroying anything, stop the database in the RDS
console (**Actions → Stop temporarily**) or in CloudShell:
`aws rds stop-db-instance --db-instance-identifier invoiceiq-dev-postgres`.
AWS restarts it automatically after 7 days. The state bucket (`bootstrap`)
has `prevent_destroy` and costs cents.
