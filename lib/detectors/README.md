# Explainable invoice detection (PLAN-03)

All six functions in `rules.ts` are pure: pass an `Invoice`, related rows, and
optional `RuleConfig`; receive a shared `NewAnomaly` or `null`. IDs/timestamps
are generated by the database, `method` is `rule`, `score` is null, and status
is always `Needs review`. These are recommendations, not rejections or fraud
determinations. `runRules` builds related-row indexes and runs each detector.

## Rules and evidence

Every finding has `summary` and batch-added `groundTruthExceptionIds` (possibly
empty). All money is USD unless `currency` explicitly identifies native money.
Priorities are High for >= USD 50,000 or >= 30 overdue days, Medium for >= USD
10,000, otherwise Low. Duplicate candidates have a minimum Medium priority.
Thresholds live in `config.ts` and can be overridden by the batch `--config`
JSON option; no source edit is required. The initial defaults are tunable
heuristics, not calibrated business policies.

| Function / Category | Condition | Evidence fields beyond the common fields |
| --- | --- | --- |
| `detectDuplicateInvoice` / Duplicate invoice | Same supplier/currency, USD amount within 0.01, dates within 7 calendar days, normalized invoice number equal or one edit apart (minimum 6 characters for near matches) | `matchedInvoiceId`, `invoiceNumber`, `matchedInvoiceNumber`, `amountUsd`, `matchedAmountUsd`, `daysApart`, `matchType`, `dateWindowDays`, `amountToleranceUsd` |
| `detectMissingPo` / Missing PO | `po_id` is null | `amountUsd`, `approvalLevel` |
| `detectPriceQuantityMismatch` / Price/quantity mismatch | Line multiplication or sum-to-net mismatch; or cumulative complete PO lines exceed PO value; a Closed PO must fully reconcile | `poId`, `currency`, `poAmount`, `invoiceLinesTotal`, `poInvoicedTotal`, `netAmount`, `lineNetDifference`, `difference`, `differencePct`, `tolerance`, `poMismatch`, `lineNetMismatch`, `inconsistentLines` |
| `detectTaxTotalError` / Tax/total error | Gross differs from net plus tax beyond currency tolerance | `currency`, `netAmount`, `taxAmount`, `grossAmount`, `expectedGrossAmount`, `difference`, `tolerance` |
| `detectOverdueInvoice` / Overdue invoice | Unpaid and due before the supplied UTC as-of date; or linked payment has positive `days_vs_due` | Unpaid: `dueDate`, `asOfDate`, `daysOverdue`, `invoiceStatus`; paid late: `dueDate`, `paidAt`, `daysVsDue`, `paymentId` |
| `detectUnusualVendorTransaction` / Unusual vendor transaction | USD amount strictly greater than 3x supplier's prior-date mean, at least 3 earlier invoices, positive baseline | `amountUsd`, `vendorAvgUsd`, `ratio`, `threshold`, `vendorInvoiceCount`, `comparisonGroup` |

JPY tolerance is 1 yen; other supported currencies use 0.01 native units. An
exact tolerance boundary is accepted, including floating-point rounding noise.
PO native amounts are never compared with USD or a different currency/supplier.
`inconsistentLines` contains `invoiceLineId`, `quantity`, `unitPrice`,
`lineAmount`, `expectedLineAmount`. `difference` is comparison total minus PO
amount; `lineNetDifference` separately describes invoice line/net reconciliation.
Zero-value POs have null `differencePct` rather than infinity.

Open/Partially invoiced POs can legitimately be billed below their full value.
Cumulative PO mismatch is attributed only to the final date/ID-sorted linked
invoice. Missing lines disable that cumulative check rather than pretending
they are zero. This requires the complete PO invoice set: do not evaluate a
Closed PO from an arbitrary subset. The dataset has no PO line quantities or
prices, so this rule cannot prove which supplier price/quantity was incorrect.
Invoice/line arithmetic is independently checked where data is available.

Duplicate detection does not flag unrelated invoice numbers on amount alone;
periodic same-value invoices can be legitimate. Both members of a matching
pair can be flagged, with one deterministic best match in each finding.
Blank numbers are not duplicate evidence. All date windows are inclusive.
Vendor baselines exclude the current invoice, same-date invoices, and future
invoice dates. UTC is assumed for dataset timestamps without an offset.

## Batch and validation

From the repository root:

```powershell
npm run test:detectors
npm run anomalies:batch -- --source fixture --as-of 2026-10-08
npm run anomalies:batch -- --source csv --dataset datasets/G_finance/G_finance --as-of 2026-10-08 --report-out reports/anomalies/rules.json
npm run anomalies:batch -- --source db --as-of 2026-10-08 --persist
```

CSV inputs are the curated `invoices.csv`, `invoice_lines.csv`,
`purchase_orders.csv`, `payments.csv`, and `invoice_exceptions.csv`. Parsing
uses `csv-parse`, validates the shared Zod schemas, converts documented numeric
columns, and interprets blanks only in nullable columns. BOM/whitespace handling
is disclosed; required blank numbers, invalid enums, and duplicate invoice IDs
are rejected. Dirty raw datasets belong in the separate ingestion-cleaning path.

Database input uses the shared Drizzle client and a read-only repeatable-read
snapshot. Run PLAN-01 migrations and PLAN-02 loading first. Persistence requires
`--source db`; it cannot accidentally write synthetic fixture IDs to production.
`saveAnomalies` inserts in a transaction and skips conflicts on the existing
invoice/method/category unique key. It never resets human status or overwrites
existing evidence/explanations. Reruns do not remove earlier findings; refreshing
or retiring them is a separate, explicit human-reviewed workflow.

Example override file contents:

```json
{
  "duplicateWindowDays": 5,
  "vendorAmountMultiplier": 4,
  "minimumVendorHistory": 5,
  "roundingTolerance": { "JPY": 2 }
}
```

Pass its path with `--config <path>`. `--as-of` controls unpaid overdue checks,
not time travel of the entire dataset: recorded paid-late events and PO state
are evaluated from the supplied snapshot.

Validation deduplicates invoice/category pairs and maps Duplicate suspected,
Missing PO, Price mismatch/Quantity mismatch, and Tax error to the respective
rules. Overdue/vendor rules have no corresponding exception labels; their
precision/recall is null, not invented. Bank details changed and Missing goods
receipt are reported as unsupported labels. No predictions or no positive labels
also produce null denominators. Label agreement is not proven fraud accuracy;
unmatched alerts may be true issues missing from upstream labels.

See [the validation report](../../docs/ANOMALY_VALIDATION.md) for verified local
results and the real-data checks that remain pending.
